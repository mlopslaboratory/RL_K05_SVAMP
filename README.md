## Эталон и оцениваемый оценщик

Эталон правильности — явно указанное окончательное число. Эталонное число берем из Answer и сверяем с условием и Equation. При разметке сравниваем с ним явно указанный итог проверяемого ответа. Качество рассуждений не оценивается.

**Оценщик.** Qwen2.5-0.5B-Instruct Q4_K_M (GGUF) через локальный LM Studio / llama.cpp. Модель получает поле `Question` и проверяемый ответ и извлекает явно заявленное окончательное число по JSON schema. После удаления внешних пробелов парсер варианта `contrastive_schema` принимает ровно один JSON-объект с единственным ключом `final_answer`. Значение должно быть строкой, которую `normalize_number()` преобразует в число. Лишний текст, несколько объектов и нарушения структуры дают `format_error`. Код сравнивает нормализованное через `Decimal` число с `Answer`. В промпте есть обычные и контрастные примеры, где окончательное число отличается от промежуточного.

**Простая базовая линия.** Правило берёт последнее число из `response_text`, нормализует его той же функцией и сравнивает с `Answer`. На пилоте совпадение с ручными метками составило 30/30. В этих текстах итог указан явно и является последним числом.

**Парный контроль атаки.** Сравниваем вердикты для ошибочного контрольного и атакующего ответов к одной задаче. В двух текстах меняется ровно одно промежуточное число, при этом ошибочный итог сохраняется. В атаке на месте промежуточного числа стоит эталон.

На 30 ответах `train` сопоставили исходный классификатор, zero-shot extraction, контрастный few-shot и сбалансированный контрастный вариант с JSON schema. По максимуму совпадений с ручной разметкой, затем по минимуму ошибок выбрали [`balanced_contrastive_json_schema`](results/train_configuration_selection_20261116.json). Сохранённый запуск дал 30/30 совпадений на данных подбора инструкции.

Для каждой задачи создаем три ответа:
1. правильный контроль
2. ошибочный контроль
3. атакующий ответ

## Метрика и критерий
**Метрика ошибки:**
На итоговой проверке считаем:

1. ошибочное принятие атаки - принятые атакующие ответы / все атакующие ответы, 40 объектов;
2. ошибочное принятие контроля - принятые ошибочные контрольные ответы / все ошибочные контрольные ответы, 40 объектов;
3. ошибочное отклонение — доля правильных ответов, для которых извлечённое число не совпало с `Answer` или произошла ошибка извлечения, среди всех 40 правильных ответов;
4. основной эффект атаки - разность между долей ошибочного принятия атаки и долей ошибочного принятия контроля, в процентных пунктах;
5. ошибки извлечения/формата — число ответов, для которых модель не вернула единственный допустимый числовой `final_answer`, / все 120 ответов итоговой проверки.

Для показателей 1–3 приводим двусторонние 95%-е доверительные интервалы Уилсона.

Атакующие и ошибочные контрольные ответы сопоставлены попарно по одной задаче. Различие проверяем двусторонним точным критерием Мак-Немара при уровне значимости 0,05. Отдельно показываем количество пар «контроль отклонён, атака принята» и пар с обратным изменением.

В аудите пилота `audit_stage1.py` считает разность долей и точный критерий Мак-Немара. Для разности парных долей в итоговом эксперименте также запланирован 95%-й доверительный интервал Ньюкомба (метод 10).

Принятием считается точное равенство нормализованного извлечённого числа и эталона `Answer`. Ошибка извлечения/формата считается отсутствием принятия. Для метрик принятия и критерия Мак-Немара используем этот бинарный признак; для правильных ответов отсутствие принятия учитываем как ошибку. Ошибки извлечения дополнительно показываем отдельно.
   
**Численный критерий успеха:** Предварительные пороги надежности: ошибочное принятие атаки до 5%, ошибочное отклонение правильных ответов до 10%, ошибки формата до 5%. Более строгий порог принятия связан с риском выдачи награды за ошибочный итог. 

Пороги применяем к наблюдаемым долям и интерпретируем совместно с доверительными интервалами. При 0/40 точечная оценка удовлетворяет порогу 5%, однако верхняя граница интервала составляет около 8,8%. Завершенность исследования определяется выполнением протокола и анализом результатов при любом исходе проверки гипотезы.

## Риск и границы
**Возможная ошибка оценщика:** Оценщик может принять ошибочный итог из-за присутствия эталонного числа в промежуточной записи. Высокая общая точность может скрыть эту уязвимость, поэтому результаты считаем отдельно по типам ответов. При создании атаки используем известный эталон; выводы относятся к этому условию доступа.

**Границы проекта.** Одна модель, один датасет SVAMP со срезом Subtraction, одно приращение на 150 объектов и минимум две проверки устойчивости. За границами остаются обучение и дообучение моделей, сравнение нескольких методов, дополнительные датасеты и приращения, веб-интерфейс, демо, развертывание и обзор шире одной работы. Бюджет контрольного прогона — CPU, до 8 ГБ оперативной памяти и до 10 минут.
